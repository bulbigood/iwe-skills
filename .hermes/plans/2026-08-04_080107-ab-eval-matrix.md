# Multi-Skill, Multi-Runtime A/B Evaluation Implementation Plan

> **For Hermes:** Implement this plan task-by-task with test-driven development and review each commit for specification compliance before proceeding.

**Goal:** Extend the existing behavioral eval harness so one experiment can compare any `N >= 2` skill/runtime targets across `X >= 1` paired samples and an explicit subset of scenarios, with an independently configured and exact-version-verified IWE runtime for every target.

**Architecture:** Keep the existing scenario definitions, independent fixture oracle, judge command, seven metrics, per-metric thresholds, and fail-closed validity model as the single evaluation pipeline. Add a schema-validated experiment manifest that expands into a matrix of `target × scenario × sample_index`; each target combines one skill payload with its own IWE runtime declaration and stable label. Aggregate each target independently first, then build a comparison layer from paired threshold outcomes and raw count distributions—never weighted totals or averages of ordinal scores.

**Tech Stack:** Python 3.11+, `argparse`, `dataclasses`, `tomllib`, JSON Schema, existing `tests/eval/run.py`, existing `scripts/skill_manifest.py`, `unittest`.

---

## Requirements and invariants

1. An experiment declares `N` uniquely labelled targets. Each target has its own skill path/id and its own IWE version, binary source, and optional source directory.
2. A target identity is the pair `(skill payload, exact IWE version)`, represented by a stable `target_id`. Results from different pairs must never share an aggregate bucket.
3. Every target runs the same selected scenario IDs and the same sample indices. Fixture commit, prepared initial state, user request, scoring rubric, judge command/model, score scale, and required success percentages are identical across targets.
4. The judge is target-blind wherever practical. Skill name, target label, and IWE version are report provenance, not correctness hints in the judge prompt.
5. The declared IWE binary is resolved deterministically and checked with `iwe --version` before any paid run. No fallback to the first `iwe` on host `PATH`.
6. Existing single-skill CLI behavior remains supported.
7. Invalid samples remain fail-closed and visible. They are never retried silently, dropped, or excluded from a denominator.
8. Each target receives its own ordinary absolute verdict using the existing metric thresholds. Relative comparison cannot turn an absolute FAIL into PASS.
9. Ordinal scores are not averaged or combined into a weighted ranking. Comparison uses threshold success, validity, raw score counts, and direct efficiency telemetry.
10. Reports contain enough provenance to reproduce every cell: target ID, skill path/version/hash, declared and observed IWE version, resolved binary/source, scenario ID, sample index, fixture commit, agent/judge config, and raw report path.

## Chosen design

### Experiment manifest

Create `tests/eval/experiments/*.toml`, separate from root `config.toml`.

Reason: root `config.toml` describes maintained release skills and their default runtime contract. An A/B experiment must also support comparing the same skill against multiple IWE versions and deprecated/unreleased skill payloads without pretending each pair is a maintained release. Putting runtime overrides in the model/judge JSON config would also mix unrelated concerns.

Proposed minimal format:

```toml
schema_version = 1
name = "iwe-skill-runtime-comparison"
scenarios = [
  "one-call-bounded-discovery",
  "apply-a-guarded-structured-block-update",
]
samples = 5
jobs = 3
agent_judge_config = "codex"

[[targets]]
id = "v18-on-0180"
skill_path = "skills/iwe-v18"
skill_version = "0.2.0"
contract_file = "contracts/iwe-v18.json"

[targets.runtime]
cli = "iwe"
source = "directory"
directory = ".runtimes/iwe-0.18.0/bin"
version = "0.18.0"

[[targets]]
id = "legacy-on-017x"
skill_path = "skills/iwe-memory-system"
skill_version = "0.0.67"
contract_file = "contracts/iwe-v17.json"

[targets.runtime]
cli = "iwe"
source = "directory"
directory = ".runtimes/iwe-0.17.x/bin"
version = "0.17.x"
```

`version` must be an exact version, not a range. The actual legacy version and contract file must be supplied only after inspecting and freezing that CLI; the placeholder above is illustrative and must not be committed as fact.

Supported runtime sources should initially reuse `directory`, `homebrew`, and `cargo`. If Homebrew/Cargo cannot select two installed versions unambiguously, validation must reject the manifest and require `directory`; it must not silently resolve both targets to one executable.

### Paired comparison model

Define a pairing key as `(scenario_id, sample_index)`. Every target must produce exactly one result per pairing key. Comparison fails closed if a target is missing a cell, duplicates a cell, or reports mismatched fixture/scenario provenance.

For every target and scenario report:

- valid/invalid sample counts;
- per-metric successful/total/required counts;
- absolute aggregate PASS/FAIL;
- raw score histogram `0..5` per metric;
- tool calls, IWE calls, document reads, output bytes, and other existing efficiency counts as raw distributions/counts.

For every target pair and scenario/metric report:

- paired threshold wins/ties/losses;
- valid/invalid cell comparison;
- success-rate difference in percentage points;
- raw score histogram for each side;
- efficiency deltas only for cells where both samples are valid, with excluded-cell count shown explicitly.

Do not create a single “best skill” weighted score. A summary may state dominance only when one target is no worse on every required metric and better on at least one, while still showing each target’s absolute verdict.

## Alternatives considered

- **Repeat `--skill` and add parallel `--iwe-version` flags:** rejected because positional pairing is fragile, runtime source/path does not fit cleanly, and saved experiments would be hard to reproduce.
- **Put all target variants in root `config.toml`:** rejected because experiment-specific runtime pairs are not necessarily maintained product contracts and the same skill may appear against several runtimes.
- **Run the current single-skill command N times and merge JSON afterward:** useful as a migration fallback, but rejected as the primary design because it cannot guarantee paired cells, identical selected scenarios, one judge configuration, or fail-closed matrix completeness.
- **Rank targets by mean judge score:** rejected because scores are ordinal and averaging permits compensation across failures.

## Risks and controls

- **Runtime/skill confounding:** unavoidable by design because the evaluated unit is the declared pair. Reports must never label the result as skill-only quality.
- **CLI contract incompatibility:** freeze a contract per runtime line and validate target/scenario support before paid execution.
- **Judge bias:** blind judge prompts to target identity and hash shared prompt/rubric inputs.
- **Unequal fixtures or random conditions:** pair by scenario/sample, pin fixtures, preserve the same model config, and expose missing cells.
- **Invalid-sample cherry-picking:** retain invalids, fail closed, and never auto-retry or exclude them.
- **Ordinal-score misuse:** publish histograms and threshold outcomes, not means, medians, or weighted totals.
- **Unbounded cost:** validate matrix size and print `2 × N × scenario_count × X` total model invocations before requesting authorization.
- **Concurrency interference:** use one global bounded executor and isolated HOME/workspace/telemetry per cell.
- **Multiple installed IWE versions:** prefer explicit per-target directories; reject ambiguous package-manager resolution.
- **Deprecated skill support:** do not invent an IWE compatibility version. Establish it from an actual binary/contract before adding that target to a real experiment.

## Definition of done

- A manifest can describe any `N >= 2` uniquely identified skill/runtime targets.
- Every target declares and exact-version-verifies its own IWE runtime.
- The runner executes selected scenarios for exactly `X` paired samples per target.
- Agent workspaces/runtimes are isolated; judge implementation, metrics, rubric, and fixture oracle are shared.
- Every target gets its own fail-closed absolute aggregate verdict.
- Pairwise comparison reports threshold wins/ties/losses, validity, raw score distributions, and efficiency evidence without ordinal averages or weighted ranking.
- Matrix completeness and provenance are deterministic-test covered.
- Single-skill CLI remains compatible.
- A paid smoke run produces verified, separated, auditable reports.
